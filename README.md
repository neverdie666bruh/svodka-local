# Сводка Локал

Отдельное приложение и отдельный сборщик ежедневной сводки на русском. Телефон только скачивает уже собранный JSON. Отбор делает обычная программа по лентам RSS/Atom и правилам ключевых слов. Здесь нет агента, нет модели, нет платного API, нет ключей и нет регистрации. Версия приложения 1.1 не обещает смысловой разбор: она шире покрывает те же 13 тем и честно показывает, где свежих пунктов нет.

Это не продолжение другого дайджеста. Свой `applicationId` — `com.urmindkilla.svodkalocal`, своя подпись, свои ленты, своя ветка `data`, своё расписание. Удаление этого проекта не должно затрагивать что-либо ещё, и наоборот. Чужой адрес данных сюда не подставлен.

## Что получается на выходе

Один выпуск на календарную дату `Asia/Dushanbe`. В нём от 0 до 20 пунктов. Если правил прошло меньше восьми, список короче: пустые места не заполняются. Каждый пункт — заголовок, ссылка на оригинал и короткий фрагмент, который отдала сама лента. Фрагмент обрезан и очищен от HTML. Полная статья не скачивается.

В карточке всегда два ярлыка: «материал источника» и «не проверено независимо». Рядом — детерминированные метки: какие слова совпали и какой получился счёт. Это не оценка важности, не мнение и не проверка факта по второму источнику. Отдельных «точек зрения» и вердикта нет: их нельзя честно собрать без разбора текста, а разбора здесь нет.

Темы: ИИ, гаджеты, программирование, железо, безопасность, космос, мозг, игры, аниме, музыка, книги, странности, мир. Криптовалюта отсекается всегда. Также отсекаются финансы и бизнес, спорт и киберспорт, автомобили, образ жизни, медицина и наука вне мозга и космоса, кино и сериалы кроме аниме, концерты и туры, светская хроника, криминал, религия и кликбейт. Книги проходят только со словами фантастики, хоррора или комикса. Космос без SpaceX, ракетного бизнеса и запусков ради запуска. Мир — только если в заголовке есть два сильных маркера крупного события; иначе пункт молча опускается. Текст пункта должен быть в основном русским. Официальные латинские имена продуктов сохраняются.

Окно — 36 часов. Повтор за последние 7 дней убирается по каноническому URL (без `utm_*` и других меток) и по похожести токенов заголовка. Совпадение токенов — это не «существенное развитие сюжета»: если заголовок почти тот же, пункт не попадёт снова.

Лайк, дизлайк и закладки живут только на телефоне и никуда не отправляются. Они меняют порядок уже скачанного выпуска. Дизлайки не удаляют тему: штраф ограничен, один-два голоса категорию не стирают. Жёсткие исключения сильнее любой оценки.

## Как устроено

```text
ленты RSS/Atom
    → сборщик на GitHub Actions (обычный код)
    → JSON в ветке data
    → телефон читает index.json и файл даты
```

Сборщик не зависит от этого компьютера и не держит никакой агент. Когда репозиторий создадут и включат расписание, job сам запустится на стандартном runner GitHub.

Ветка `data` содержит только текст: `public/index.json`, `public/ГГГГ-ММ-ДД.json`, `state/seen.json`, `state/last-run.txt`, короткий README. Персональных оценок там нет. Старые файлы выпусков не удаляются. Бинарники в эту ветку не коммитятся.

Адрес указателя уже вшит: `https://raw.githubusercontent.com/neverdie666bruh/svodka-local/data/public/index.json`. Это публичное чтение без ключа. Поля для своего адреса нет. Телефон при открытии и по кнопке «Загрузить» скачивает этот указатель и один файл выпуска, кладёт их во внутреннее хранилище и показывает архив. Если сети нет, остаётся последняя сохранённая копия и текст ошибки. Если дата выпуска не совпадает с сегодняшним днём в `Asia/Dushanbe`, на экране явная пометка, что это не сегодняшний выпуск. Ссылки открываются во внешнем браузере. WebView нет.

Расписание на телефоне не ставится. Нет уведомлений, нет разрешения на уведомления, нет foreground-service, нет WorkManager.

## Расписание и почему минута не точная

Цель — утро в `Asia/Dushanbe`. В workflow записано:

```yaml
cron: "15 8 * * *"
timezone: Asia/Dushanbe
```

Это 08:15 по Душанбе, то есть 03:15 UTC. У зоны нет перехода на летнее время, она постоянно UTC+5. Правило GitHub про пропущенный час при переходе на летнее время к ней не относится.

Минута 15, а не 00, потому что документация GitHub прямо говорит: в начале каждого часа нагрузка выше, запуск могут задержать, а при сильной нагрузке часть поставленных в очередь job могут молча сбросить. Сброшенный запуск не помечается как ошибка. Он просто не происходит.

Другие ограничения из той же документации:

- расписание срабатывает только если файл workflow лежит на ветке по умолчанию, и запускается только она;
- в публичном репозитории расписание само отключается, если 60 дней не было активности репозитория;
- минимальный интервал cron — 5 минут, но это не делает ежедневный запуск точным.

Дата выпуска считается по часам в момент реального запуска, в `Asia/Dushanbe`, а не по подписи cron. Если задержку унесло за полночь этой зоны, выпуск получит уже новую дату, а пропущенная дата не создаётся задним числом. Повторный запуск в ту же дату ничего не дублирует: готовый полный выпуск пропускается. Если выпуск был частичным, следующий запуск добирает только упавшие источники. Ручной `workflow_dispatch` с `force` пересобирает текущую дату. Закладки на телефоне от этого не пропадают: они хранятся отдельно от файла выпуска.

## Деньги и лимиты GitHub

Сверено с документацией GitHub 8 ноября 2026.

- Стандартные hosted runners в **публичном** репозитории бесплатны и не тратят included compute. В workflow жёстко указан `ubuntu-24.04`. Это стандартная машина, не larger runner. Larger runners тарифицируются даже в публичном репозитории.
- В **приватном** репозитории стандартные минуты сначала едят включённый лимит плана (на Free это $12 в месяц), затем могут списывать деньги. Сбор рассчитан на публичный репозиторий: первый шаг проверяет видимость и останавливается, если она не public. На приватном этот короткий запуск уже потратит минуты, поэтому workflow туда не переносить.
- Ежедневный сбор **не** вызывает `actions/cache`, `actions/upload-artifact` и Pages. Квота хранилища артефактов от него не растёт. В публичный JSON пишется обычный git-коммит через встроенный `GITHUB_TOKEN`.
- `GITHUB_TOKEN` — короткоживущий токен GitHub App этого репозитория. Это не ключ модели и не личный PAT. В APK его нет. Читает телефон публичные файлы без авторизации.
- Сборка APK — только ручной `workflow_dispatch` файла `.github/workflows/build-apk.yml`. Тег и push её не запускают. Артефакт один: `dist/svodka-local-release.apk`, хранение 1 день. Это входит в квоту хранилища Actions (на Free 500 МБ вместе с GitHub Packages; сверх неё документация указывает $0.25 за ГБ в месяц). Ежедневный сбор артефактов не создаёт.
- Коммиты от `GITHUB_TOKEN` не запускают новый workflow по `push` и не запускают сборку GitHub Pages. Поэтому страница Pages здесь не используется: JSON лежит в ветке `data` и читается как сырой файл.
- У `raw.githubusercontent.com` есть лимит на неаутентифицированные запросы. Точная цифра в актуальной документации не зафиксирована; в мае 2025 GitHub писал, что лимиты для скачивания без входа ужесточали. Один телефон, который открывает два небольших JSON, в этот лимит не целится. Если придёт отказ, приложение оставляет прошлую копию и показывает ошибку.
- GitHub Pages как запасной хостинг имеет мягкий предел около 100 ГБ трафика в месяц и сайт до 1 ГБ. Для этого проекта он не нужен и ежедневный job его не публикует.

Сбор на расписании включается файлом `.github/workflows/collect-digest.yml` на ветке `main`. Отдельная variable для него не нужна. Сборка APK включается тем же репозиторием как ручной workflow и ждёт четыре secrets подписи; без них загрузка артефакта не начинается.

## Источники

Список — `sources/rules.json` и `sources/sources.json`. Туда попадают только адреса, которые 8 ноября 2026 ответили настоящей лентой RSS или Atom по HTTPS, без ключа и без обхода защиты. Поле copyright, если лента его отдала, записано в `licenseNote`. Где его нет, так и сказано. Ни одна лента не даёт права перепечатывать статью: хранится только усечённый фрагмент и ссылка.

Живой прогон сборщика 8 ноября 2026, 09:29 UTC (14:29 по Душанбе): 34 включённых источника, выпуск `2026-11-08`, 20 пунктов, `partial: false`, около 56 КБ. По темам: программирование 4, ИИ 4, гаджеты 4, железо 4, игры 3, музыка 1. Космос, мозг, книги, аниме, странности, безопасность и мир в этот день в выпуск не попали — не потому что темы выключены, а потому что в окне 36 часов не нашлось пунктов, прошедших порог. Из 1304 записей 846 были старше окна, 356 не набрали счёт, 26 отсеялись жёсткими исключениями, 8 были повторами, 6 заголовков были не на русском, у 2 не разобралась дата. Повторный запуск в ту же дату сразу сказал `skipped=true` и сеть заново не обходил.

Аниме: 8 ноября 2026 публичная главная `https://animag.ru/` отдала датированные новости `/news/` (пример — «Дата выхода четвёртого сезона Yuru Camp», 7 ноября 2026, 09:15). Отдельного RSS нет, берётся только карточка указателя, не статья. Второй домен не подключился: КГ-Портал оборвал чтение, World-Art не открыл TLS, animego ответил 500 и 404, Shikimori — 403. Общая лента DTF остаётся играми: в проверенном снимке аниме-пунктов не было. «Наука и жизнь» выключена в списке и сама не включается: XML не разбирается. После четырёх неудач подряд включённый источник молчит до рассчитанной даты, не дольше семи суток, и затем проверяется сам. Ручной force только проверяет его сразу, это не единственный способ вернуться.

Проверенные добавления того же дня, без догадок по адресу: FantLab `https://fantlab.ru/news.rss` (книги, пункт 8 ноября), Астронет `https://www.astronet.ru/db/rss.xml` (астрономия, windows-1251), Securelist и блог Касперского (безопасность; свежие пункты часто старше 36 часов), DTF `https://dtf.ru/rss` (игры, не аниме), «Наука и жизнь» (свежий пункт в выборке от 22 октября, чаще вне окна). Не добавлены: Eksmo (лента 2009 года), AST (гороскопы и быт), «Биомолекула» `public.atom` без записей, Anti-Malware (последний пункт 2019), The Flow (RSS не найден), DARKER по-прежнему 403. `darker` один раз отдал HTTP 200, а сборщик затем трижды получил 403. Источник выключен, пока ответ нестабилен. `3dnews.ru/software/rss/` — это длинный архив на 3,4 МБ; хвост XML невалиден, поэтому читаются первые 80 записей. На 8 ноября они были старше 36 часов, в выпуск не вошли, и это не ошибка источника.

Подробная таблица проб — в `docs/sources-live-check.md`.

Чтобы добавить ленту, нужен публичный HTTPS RSS или Atom, короткая запись в `sources.json` (имя, группы, предел фрагмента, что известно про права) и при необходимости слова в `sources/rules.json`. Адрес с паролем, `localhost`, частной сетью и не-HTTPS сборщик отвергает. Сломанный источник не роняет остальные: в выпуске будет статус и, если включённые источники упали, флаг `partial`. Выключенный источник в списке остаётся, но не считается поломкой.

## Сборка

Нужны JDK 21 и Android SDK 35 (build-tools 35).

```bash
echo "sdk.dir=$ANDROID_HOME" > local.properties
bash scripts/bootstrap-gradle.sh
./gradlew :core:test :collector:test
./gradlew :app:assembleRelease
```

`local.properties` не коммитится. Debug-сборка — это debug-подпись, не выпуск.

Дистрибутив закреплён: Gradle 8.11.1, только `https://services.gradle.org/distributions/gradle-8.11.1-bin.zip`, SHA-256 `f397b287023acdba1e9f6fc5ea72d22dd63669d59ed4a289a29b1a76eee151c6` (тот же отпечаток на [gradle.org/release-checksums](https://gradle.org/release-checksums/)). `scripts/bootstrap-gradle.sh` вызывается сборщиком и сборкой APK до `./gradlew`. Адрес запрашивается по HTTPS. Если редирект отвечает 502, 503 или 504, скрипт повторяет попытку и чередует её с тем же официальным файлом `gradle/gradle-distributions` тега `v8.11.1`. Общий бюджет повторов — 8 минут. Файл принимается только если это zip и SHA-256 совпал. Чужие зеркала, `actions/cache` и загрузка архива дистрибутива в артефакты не используются. Wrapper проверяет `distributionSha256Sum` ещё раз.

Новая подпись создаётся так и больше не печатает пароль:

```bash
bash scripts/init-release-keystore.sh
```

По умолчанию файлы ложатся в `/cursor/stores/self/signing/` (`svodka-local-release.jks` и `keystore.properties`). Это отдельный ключ, RSA 2048, alias `svodka-local`, CN=Svodka Lokal. Пароль только в properties-файле. В git его нет. Пока этот каталог доступен, им можно подписывать следующие сборки. Если каталог пропадёт, новая подпись будет уже другой личностью приложения: обновление поверх старого APK не встанет. Сертификат текущего выпуска, SHA-256: `C3:4A:30:6A:D9:4E:7D:3A:E5:7A:C4:C5:03:99:8D:EE:CB:3E:32:FC:BB:FE:80:89:CC:00:72:A3:16:34:D4:2C`.

Текущая версия приложения: `versionName` 1.1, `versionCode` 2, `minSdk` 26, `targetSdk` 35, пакет `com.urmindkilla.svodkalocal`. Подпись та же, обновление ставится поверх 1.0. Схема JSON остаётся 1: новые поля имеют значения по умолчанию, старые закладки и выпуски читаются. Лайки не уходят на сервер и не меняют следующий сбор.

Workflow APK подписывает уже существующий ключ и кладёт в артефакт только `svodka-local-release.apk`. Нужны secrets репозитория, без новых ключей и без печати значений:

- `SVODKA_LOCAL_KEYSTORE_B64` — тот же JKS в base64
- `SVODKA_LOCAL_KEYSTORE_PASSWORD`
- `SVODKA_LOCAL_KEY_ALIAS` — alias существующего ключа, `svodka-local`
- `SVODKA_LOCAL_KEY_PASSWORD`

Если любого secrets нет, сборка останавливается до загрузки. После подписи workflow сверяет SHA-256 сертификата APK с отпечатком выше (`C34A306AD94E7D3AE57AC4C503998DEECB3E32FCBBFE8089CC0072A31634D42C`). Отпечаток записан в файле workflow, это не поле ручного запуска. Несовпадение останавливает job до загрузки артефакта. Debug APK, журналы, исходники и ключ в артефакты не попадают. Релиз GitHub, письмо и отправка APK в чат не делаются.

## Что нужно, чтобы сводка пошла сама

Репозиторий на GitHub отсюда не создавался. Когда будет пустой **публичный** репозиторий, отдельный от любых других проектов:

1. Запушить этот код в `main` пустого публичного репозитория `neverdie666bruh/svodka-local`. Чужую историю не перетирать.
2. Убедиться, что Actions разрешены, а runner остаётся стандартным `ubuntu-24.04`.
3. Один раз запустить workflow Collect digest вручную. Он создаст ветку `data`. Адрес в приложении уже указывает на этот репозиторий.
4. Записать четыре secrets подписи из уже сохранённого ключа и после этого вручную запустить Build APK. До появления secrets этот workflow запускать не нужно: он завершится до артефакта.

Каждый успешный запуск, даже если выпуск уже собран и сами новости не менялись, обновляет `checkedAt` в указателе. Это маленький текстовый коммит в `data`. Документация GitHub не определяет, какая именно активность сбрасывает 60-дневное отключение расписания в публичном репозитории. Ежедневный коммит — поддерживаемый способ оставлять активность, а не обещание, что расписание нельзя отключить.

## Что проверено и что нет

Проверено на JVM, 8 ноября 2026: 11 тестов, 0 падений (`:core:test`, `:collector:test`). Внутри — RSS и Atom, отказ от DOCTYPE, windows-1251, даты и граница суток Душанбе, окно 36 часов, исключения, дедуп, потолок 20 и отказ добивать список, идемпотентность, частичный повтор, обрыв сети, закладка после удаления выпуска, лайки не стирают тему, запрет частных адресов, отсутствие чужих идентификаторов и запрет ежедневных артефактов в workflow.

Живой сбор описан выше. Повтор того же дня пропустился.

Сборка release APK прошла, подпись проверяется `apksigner`. Эмулятора в этой среде нет (`emulator` не установлен), телефон не подключался. Расписание GitHub Actions тоже не запускалось: workflow только лежит в репозитории. Поведение Doze, force-stop и перезагрузки телефона для этой схемы неважно для самого сбора — сбор не на телефоне. От них зависит только то, откроет ли человек приложение и скачает уже лежащий JSON. Если телефона долго нет в сети, он увидит старую копию и подпись, что дата не сегодняшняя.
